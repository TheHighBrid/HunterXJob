# Running HunterXJob v2 on a Linux VM

This is the primary way to run v2 unattended: a small Linux VM runs the API and
the background scheduler as a systemd **user** service, and your Android phone
talks to it remotely. The API is never exposed without authentication, and it
does not need to be exposed to the public internet at all.

Nothing here enables live submission. Cycles only run dry-runs while
`ALLOW_LIVE_SUBMISSION=false` and no adapter is `certified_autonomous`.

## 1. Pick a VM

- **Oracle Cloud Always Free, Ampere A1 (arm64)**, Ubuntu 24.04. 2 OCPU / 12 GB is plenty for the API, headless Chromium and a small Ollama model. The 1 GB `E2.1.Micro` shape is too small for Chromium plus a local model.
- Any other Ubuntu 24.04 (or Debian 12+) VM with 2 GB+ RAM works. Ubuntu 24.04 ships Python 3.12, which v2 needs.
- Use SSH keys. In the cloud firewall (OCI: the subnet's security list or an NSG), allow **only TCP 22, ideally only from your own IP**. Do not open 8011.

## 2. Install

```bash
sudo apt update
sudo apt install -y git python3 python3-venv sqlite3 curl
git clone https://github.com/TheHighBrid/HunterXJob.git ~/HunterXJob
cd ~/HunterXJob/v2
./hunterx install          # creates .venv, .env and a random API_KEY (mode 600)
```

### Chromium for browser verification

Browser verification (`GREENHOUSE_BROWSER_VERIFY=true`) loads each posting's real
application page in headless Chromium, read-only, and catches required fields the
Greenhouse API omits. Turn it on for the VM:

```bash
.venv/bin/pip install -e '.[browser]'
sudo .venv/bin/python -m playwright install-deps chromium   # system libraries (apt)
.venv/bin/python -m playwright install chromium             # browser, into ~/.cache/ms-playwright
sed -i 's/^GREENHOUSE_BROWSER_VERIFY=.*/GREENHOUSE_BROWSER_VERIFY=true/' .env
```

### Optional: local model

Scoring copy and material drafting use Ollama when it is reachable at
`OLLAMA_BASE_URL`; without it, scoring is deterministic only and the cycle skips
"prepare". If you want it, install Ollama from its official instructions and pull
the models named in `.env` (`OLLAMA_FAST_MODEL`, `OLLAMA_QUALITY_MODEL`).

## 3. Configure `.env`

| Setting | Recommended on the VM |
|---|---|
| `API_KEY` | Generated by install. Keep it secret: it is the only credential. Rotate with `./hunterx api-key`, update `.env`, restart. |
| `HOST` / `PORT` | Keep `127.0.0.1` / `8011`. Reach the API through a tunnel or proxy (section 5). |
| `LOCAL_DEV_MODE` | `false`. Never `true` on a VM. |
| `TIMEZONE` | Your zone, e.g. `America/Toronto` (quiet hours and daily caps use it). |
| `GREENHOUSE_BOARD_TOKENS` / `LEVER_COMPANIES` | The boards to watch. |
| `GREENHOUSE_BROWSER_VERIFY` | `true` once Chromium is installed. |
| `AUTOMATION_ENABLED` | `true` only when you want dry-runs to run (they never submit). |
| `CONTINUOUS_RUN_ENABLED` | Start with `false`; run `./hunterx cycle` by hand first, then turn on. |
| `CYCLE_*`, `MAX_DRY_RUNS_PER_DAY` | Keep the conservative defaults until you trust the results. |
| `BACKUP_*` | Defaults keep 14 daily copies in `data/backups`. |

Then check everything:

```bash
./hunterx doctor
```

It must report `API auth OK`, `Network bind OK`, `Browser verify OK` and `Database schema OK`.

## 4. Run it as a service

```bash
./hunterx service-install                  # writes ~/.config/systemd/user/hunterxjob.service
systemctl --user enable --now hunterxjob
sudo loginctl enable-linger "$USER"        # start at boot, keep running after you log out
journalctl --user -u hunterxjob -f         # logs
systemctl --user restart hunterxjob        # after changing .env
```

The unit runs `./hunterx serve` in the foreground, restarts on failure, and uses
`UMask=0077` so the database, backups and logs are private to your user. Startup
applies pending schema migrations (backing up the database first).

## 5. Reach it from the phone without exposing it

Pick **one**. In every option the API keeps listening on `127.0.0.1` only and still
requires the `X-API-Key` header.

### A. Tailscale (recommended)

A private network between the VM and your phone. No public ports, TLS included.

```bash
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up
sudo tailscale serve --bg 8011     # https://<vm-name>.<tailnet>.ts.net -> 127.0.0.1:8011, tailnet only
```

Install Tailscale on the phone, sign in to the same tailnet, and use
`https://<vm-name>.<tailnet>.ts.net` as the server URL in the app, together with your API key. Do **not**
use `tailscale funnel`, which publishes the service to the internet.

Alternative without `tailscale serve`: set `HOST` in `.env` to the VM's
Tailscale address (`tailscale ip -4`, a `100.x.y.z` address), restart, and use
`http://<vm-name>.<tailnet>.ts.net:8011` in the app. Tailscale's WireGuard
tunnel encrypts that traffic, which is why the Android app allows cleartext
HTTP. `./hunterx doctor` will warn that `HOST` isn't loopback; that's expected
here. Never bind to `0.0.0.0` or to a public IP.

### B. Cloudflare Tunnel

`cloudflared` makes an outbound-only tunnel from the VM to a hostname on your
Cloudflare domain, so no inbound port is opened. Point the tunnel at
`http://127.0.0.1:8011`. Add a Cloudflare Access policy if you can; note that the
mobile app only sends `X-API-Key`, so an interactive Access login works for the
browser dashboard but not for the app.

### C. Public HTTPS reverse proxy (Caddy)

Only if you have a domain and cannot use A or B. Open TCP 80 and 443 in the cloud
firewall **and** the host firewall, then:

```
# /etc/caddy/Caddyfile
hunterx.example.com {
    reverse_proxy 127.0.0.1:8011
}
```

Caddy obtains the TLS certificate automatically. The API key is then the only
barrier, so keep it long and private, and consider restricting `remote_ip` to
your phone's networks.

### Never

- `HOST=0.0.0.0` with port 8011 open: plain HTTP sends the API key in clear text.
- `LOCAL_DEV_MODE=true` together with any proxy or tunnel. (The API also refuses
  local-dev requests that carry proxy headers, but do not rely on that.)
- `tailscale funnel` or an unauthenticated public tunnel.

### Host firewall notes (Oracle Ubuntu images)

Oracle's Ubuntu images ship `iptables` rules (`/etc/iptables/rules.v4`) that reject
everything except SSH. Options A and B need no change. For option C, insert accept
rules for 80/443 before the final REJECT and persist them:

```bash
sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 80 -j ACCEPT
sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 443 -j ACCEPT
sudo netfilter-persistent save
```

Use either these rules or `ufw`, not both.

## 6. Everyday control from the phone

Install the HunterXJob app (`mobile/`, see [mobile/README.md](../mobile/README.md)).
On first launch it opens **Connection**:

1. **Server URL**: the URL from section 5, e.g. `https://<vm-name>.<tailnet>.ts.net`
   or `http://<vm-name>.<tailnet>.ts.net:8011`. There is no built-in default.
2. **API key**: `API_KEY` from `v2/.env`. It is kept in Android's secure storage (Keystore).
3. **Test connection**: checks that the URL is valid, that the server is
   reachable, that the key is accepted, and that the server version is at least 0.4.0.

From then on:

* **Dashboard** shows status, the kill switch, scheduler pause/resume/run-now, today's caps and recent cycles.
* **Jobs** and **Review** let you approve, reject or resolve tasks.
* **Reports** shows counts.
* **Settings** lets you change caps, score threshold, quiet hours, cycle limits and targeting.

Live submission is shown as locked, and nothing in the app can unlock it.

The same calls with curl, with `BASE` set to the server URL and `KEY` to your API key:

```bash
curl -H "X-API-Key: $KEY" $BASE/api/scheduler/status            # what is it doing?
curl -H "X-API-Key: $KEY" "$BASE/api/scheduler/cycles?limit=5"  # recent cycles
curl -X POST -H "X-API-Key: $KEY" $BASE/api/scheduler/run       # run a cycle now
curl -X POST -H "X-API-Key: $KEY" $BASE/api/scheduler/pause     # pause cycles (resume: /resume)
curl -X POST -H "X-API-Key: $KEY" -H 'Content-Type: application/json' \
     -d '{"engaged": true, "note": "stop"}' $BASE/api/kill-switch   # stop everything
curl -H "X-API-Key: $KEY" $BASE/api/review-tasks                # what needs you
curl -H "X-API-Key: $KEY" $BASE/api/reports/summary             # counts
```

Disengaging the kill switch needs `"confirm": true` in the body. The browser
dashboard at `$BASE/` covers the operator routes (paste the key once).

## 7. Backups and updates

- Backups land in `data/backups` (mode 600). Copy them off the VM regularly, e.g.
  `scp vm:HunterXJob/v2/data/backups/*.db ~/hunterx-backups/` or `rclone`.
- Restore: `systemctl --user stop hunterxjob`, copy a backup over `data/hunterxjob-v2.db`,
  remove `data/hunterxjob-v2.db-wal` and `-shm` if present, start again.
- Update:

  ```bash
  cd ~/HunterXJob && git pull
  cd v2 && .venv/bin/pip install -e '.[browser]'
  systemctl --user restart hunterxjob   # migrations run on start, after a backup
  ./hunterx doctor
  ```

## Fallback: Termux on the phone

If there is no VM, v2 can run on the phone itself: install Termux and the
Termux:Boot app, clone the repo, `./hunterx install`, `./hunterx boot-install`, open
Termux:Boot once, and exempt Termux from battery optimisation. Keep `HOST=127.0.0.1`.
Playwright/Chromium does not run on plain Termux, so browser verification is not
available there; treat dry-run results as API-only (`dom_verified=false`).
