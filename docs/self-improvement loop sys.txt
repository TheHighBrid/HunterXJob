 the right way is not to let the system freely rewrite itself in production. The practical approach is to build a controlled improvement loop: observe each run, detect failures, score them with evals, propose changes, test those changes in a sandbox, promote only the versions that beat the baseline, and keep rollback/human approval for risky changes. [1][2]

Core pattern

What you want is usually called a closed-loop agent improvement system or self-evolving agent workflow, where traces, structured feedback, and repeatable evals drive better prompts, tool logic, routing, and sometimes code changes over time. [1][3]

The key design rule is this: every attempt should generate a run record, that run should be graded, the failure should be turned into a concrete fix candidate, and the candidate should only ship if it wins against the current version on a stable test set. [1][2]

Safe architecture

Use this 8-stage loop for all your products.

1. Run the task with full tracing, including inputs, outputs, tool calls, latency, errors, retries, and final result. [1]
2. Classify failures, for example wrong answer, bad tool choice, timeout, hallucination, invalid form submission, unsafe action, UI breakage, or poor user experience. [4]
3. Score each run with evals, using deterministic checks where possible and LLM-as-judge only where needed. [2][5]
4. Extract a patch candidate, such as prompt update, selector threshold change, workflow branch fix, retrieval tweak, or code diff. [3]
5. Test the patch in a sandbox against regression suites plus recent failed cases. [2][5]
6. Promote only if metrics improve and guardrails still pass. [6]
7. Version everything, including prompts, tool schemas, policies, datasets, and code. [1]
8. Keep rollback and human escalation when confidence is low or the retry budget is exhausted. [3][7]

Do not start with fully autonomous code rewriting across the whole stack. Multi-agent and self-modifying systems add nondeterminism and complexity, so they should be introduced only when evals show a simpler architecture is no longer enough. [7][2]

Self-rewrite boundaries

You should separate what the system may change automatically from what must require approval. [7]


Auto-change allowed
Approval required

Prompts, tool descriptions, routing rules, retry strategy, ranking weights, non-critical UI text [3]
Payment logic, auth, permissions, data deletion, browser automation on live accounts, code touching security or compliance paths [6][7]

Test generation, failure clustering, draft code patches, config tuning [2]
Production DB migrations, secret handling, external side effects, anything with legal or safety risk [6][4]



A strong rule for your stack is: let the system author code, but require a gated pipeline to execute, test, compare, and approve it before merge or deployment. That preserves constant learning without turning production into a live experiment.

Blueprint

The production pattern used in current agent cookbooks is not “the model rewrites itself live.” It is traces plus human and model feedback, turned into reusable evals, then into harness changes (instructions, tools, routing, output contracts, validation checks) that a coding agent implements and a validation gate accepts or rejects. [1][2]

text
Task run
  -> trace (spans: model, tools, handoffs, guardrails)
  -> deterministic graders + LLM-as-judge
  -> failure cluster + diagnosis
  -> candidate harness (prompt / policy / tool schema / code diff)
  -> sandbox eval CI
  -> champion vs challenger
  -> promote only if score rises AND guardrails pass
  -> else rollback and escalate


OpenAI’s improvement loop closes exactly this cycle: new traces, human and model feedback, generated evals, diagnosis, implementation, validation, and deployment all feed the next cycle. A heartbeat worker can pick up handoff artifacts and start the next implementation pass. [1]

The self-evolving retraining loop is the same idea at prompt level: baseline agent, human or LLM-as-judge feedback, evals and an aggregated score, then replace the baseline only after the score clears a threshold (example targets around 0.8) or stop after a retry cap and alert a human. [2]

A trace is the full run record. Trace grading assigns scores so you can see whether the agent chose the wrong tool, skipped a check, or only failed at the final answer. Once the failure mode is clear, move from one-off trace inspection to datasets and repeatable eval runs. [4][3]

Judge design

Do not use the LLM-as-judge as the only signal. The reliable pattern mixes cheap deterministic graders with one rubric judge. [2]

• Deterministic graders catch exact failures: required files exist, schema is valid, chemical names are preserved, length is in band, citations point at real files. [2][1]
• Similarity or coverage checks catch drift away from source material. [2]
• The LLM-as-judge scores nuance the rules miss, using a fixed rubric and a numeric range such as 0 to 1 with an explicit pass threshold. [2]
• Aggregate with a simple rule, for example average score and a pass ratio. One published loop treats a candidate as a lenient pass if at least 75% of graders pass or the average is at least 0.85, then keeps the version with the best cumulative score. [2]

Calibrate the judge against a small human-labeled set before you trust it in CI. Online scoring (latency, cost, user thumbs, near-real-time judge) is for monitoring; offline datasets are for promotion decisions. [5][4]

Error correction loop

Each failed run should become a structured defect, not a free-text complaint.

1. Capture the trace, final artifacts, and any user signal. [1][5]
2. Run graders. Parse per-grader score, pass/fail, and reasoning. [2]
3. Cluster repeated failures across traces (wrong tool, missing citation, policy miss, bad handoff). Macro-evals exist specifically to find recurring patterns in multi-agent runs. [6]
4. Feed the original harness, the bad output, and the grader reasoning into a metaprompt agent whose only job is to write a stricter next harness. [2]
5. Re-run the full eval set, not the single failed example. [4][2]
6. Keep the best aggregate scorer. If retries hit the cap, stop and page a human. [2]

The metaprompt itself should stay relatively static. Version the task harness; do not let the optimizer rewrite its own instructions every cycle. [2]

• Frozen golden set that never gets overwritten by the optimizer.

• Score must beat champion, not merely pass a lenient bar. [2][1]

Core components

1. Runtime agent

Every application should execute tasks through a common runtime wrapper:

python
result = await improvement_runtime.run(
    project="hunterxjob",
    task_type="job_application",
    input_payload=payload,
    agent_version="champion",
)


The runtime should automatically create:

• run_id
• trace_id
• project
• task_type
• agent_version
• input and output hashes
• model calls
• tool calls
• tool arguments
• tool results
• errors and retries
• latency and cost
• generated artifacts
• user feedback
• final success or failure state

Use a standardized trace format such as OpenTelemetry-style spans. Current GenAI conventions model agents, tasks, actions, artifacts, teams, and memory as related observability objects, which fits your multi-project architecture well. [3][4]

A trace should look conceptually like this:

    "job_url": "https://example.com/job/123"

2. Run and artifact store

For your cost-conscious deployment style, begin with PostgreSQL plus object storage rather than introducing a large distributed platform.

3. Failure taxonomy

The system cannot improve reliably if every error is just “something went wrong.” Define a controlled taxonomy.

text
MODEL:
  hallucination
  unsupported_claim
  bad_format
  incomplete_answer
  inconsist


the right way is not to let the system freely rewrite itself in production. The practical approach is to build a controlled improvement loop: observe each run, detect failures, score them with evals, propose changes, test those changes in a sandbox, promote only the versions that beat the baseline, and keep rollback/human approval for risky changes. [1][2]

Core pattern

What you want is usually called a closed-loop agent improvement system or self-evolving agent workflow, where traces, structured feedback, and repeatable evals drive better prompts, tool logic, routing, and sometimes code changes over time. [1][3]

The key design rule is this: every attempt should generate a run record, that run should be graded, the failure should be turned into a concrete fix candidate, and the candidate should only ship if it wins against the current version on a stable test set. [1][2]

Safe architecture

Use this 8-stage loop for all your products.

1. Run the task with full tracing, including inputs, outputs, tool calls, latency, errors, retries, and final result. [1]
2. Classify failures, for example wrong answer, bad tool choice, timeout, hallucination, invalid form submission, unsafe action, UI breakage, or poor user experience. [4]
3. Score each run with evals, using deterministic checks where possible and LLM-as-judge only where needed. [2][5]
4. Extract a patch candidate, such as prompt update, selector threshold change, workflow branch fix, retrieval tweak, or code diff. [3]
5. Test the patch in a sandbox against regression suites plus recent failed cases. [2][5]
6. Promote only if metrics improve and guardrails still pass. [6]
7. Version everything, including prompts, tool schemas, policies, datasets, and code. [1]
8. Keep rollback and human escalation when confidence is low or the retry budget is exhausted. [3][7]

Do not start with fully autonomous code rewriting across the whole stack. Multi-agent and self-modifying systems add nondeterminism and complexity, so they should be introduced only when evals show a simpler architecture is no longer enough. [7][2]

Self-rewrite boundaries

You should separate what the system may change automatically from what must require approval. [7]


Auto-change allowed
Approval required

Prompts, tool descriptions, routing rules, retry strategy, ranking weights, non-critical UI text [3]
Payment logic, auth, permissions, data deletion, browser automation on live accounts, code touching security or compliance paths [6][7]

Test generation, failure clustering, draft code patches, config tuning [2]
Production DB migrations, secret handling, external side effects, anything with legal or safety risk [6][4]



A strong rule for your stack is: let the system author code, but require a gated pipeline to execute, test, compare, and approve it before merge or deployment. That preserves constant learning without turning production into a live experiment.

Apply to your apps

For your projects, I would not build one giant self-improving brain first. Based on your preference for pragmatic, robust, fail-closed systems and avoiding unnecessary rewrites, the better path is one shared improvement platform with per-product evals and guardrails. [8][9][10]

HunterXJob

Treat it as a browser automation and decision-quality system. Log every page visited, field extracted, form fill, rejection reason, anti-bot event, and successful submission; then grade runs on extraction accuracy, form validity, duplicate avoidance, and submit success rate. [1]

Auto-improvements here should focus on selector repair, form-mapping rules, resume-answer consistency, and retry strategy, while live submission actions should stay gated because wrong actions can damage accounts or send bad applications. [6][4]

Allo / virtual GF

Treat it as a real-time conversation quality loop. Capture interruption timing, latency, turn-taking, speech naturalness feedback, reconnection quality, and persona consistency, then optimize prompts, buffering, barge-in logic, memory policy, and voice settings rather than letting it rewrite core telephony logic freely. [10]

This matches your earlier Allo direction: improve realism through audio pipeline behavior, interruption handling, and session recovery before broader architecture changes. [10]

Fidelis

Fidelis is already well suited for this style because it emphasizes provenance, validation, and trustworthy outputs. Use failed cases to learn which restoration profile, model family, tile strategy, or artifact detector works best by content type, but keep fail-closed checks so the system never silently promotes hallucinated or over-sharpened output. [9][11]

A good loop here is: image in, multi-profile candidates, score with regional metrics plus artifact detectors, compare against benchmark set, then promote the winning profile or model only if it beats the baseline across the held-out suite. [9][2]

Pedit

Treat it as a precision transformation system. Track whether edits preserved layout, text positions, fonts, tables, metadata, OCR alignment, and export correctness, and use those failures to improve operation planners and patch generators. [5]

Auto-writing code is acceptable here mainly for parser adapters, layout heuristics, and test fixtures, but file corruption paths should require approval because users expect exactness. [6]

Agent Gang

Start with a single orchestrator plus a few specialist tools, not a swarm first. The guidance is clear that multi-agent designs increase handoff errors and should be justified by evals rather than assumed up front. [7][2]

For Agent Gang, the learning loop should score tool choice, argument correctness, task completion, and unnecessary handoffs; only split into more agents after the eval data proves one agent can no longer manage the task surface well. [4]

Judge design

Do not use the LLM-as-judge as the only signal. The reliable pattern mixes cheap deterministic graders with one rubric judge. [2]

• Deterministic graders catch exact failures: required files exist, schema is valid, chemical names are preserved, length is in band, citations point at real files. [2][1]
• Similarity or coverage checks catch drift away from source material. [2]
• The LLM-as-judge scores nuance the rules miss, using a fixed rubric and a numeric range such as 0 to 1 with an explicit pass threshold. [2]
• Aggregate with a simple rule, for example average score and a pass ratio. One published loop treats a candidate as a lenient pass if at least 75% of graders pass or the average is at least 0.85, then keeps the version with the best cumulative score. [2]

Calibrate the judge against a small human-labeled set before you trust it in CI. Online scoring (latency, cost, user thumbs, near-real-time judge) is for monitoring; offline datasets are for promotion decisions. [5][4]

Error correction loop

Each failed run should become a structured defect, not a free-text complaint.

1. Capture the trace, final artifacts, and any user signal. [1][5]
2. Run graders. Parse per-grader score, pass/fail, and reasoning. [2]
3. Cluster repeated failures across traces (wrong tool, missing citation, policy miss, bad handoff). Macro-evals exist specifically to find recurring patterns in multi-agent runs. [6]
4. Feed the original harness, the bad output, and the grader reasoning into a metaprompt agent whose only job is to write a stricter next harness. [2]
5. Re-run the full eval set, not the single failed example. [4][2]
6. Keep the best aggregate scorer. If retries hit the cap, stop and page a human. [2]

The metaprompt itself should stay relatively static. Version the task harness; do not let the optimizer rewrite its own instructions every cycle. [2]

Start with one agent, one harness, and trace grading. Multi-agent systems need extra evals for tool choice, delegation, and review pauses; add specialists only after the single-agent evals show a real routing problem. [6][4]

Also keep the optimizer outside the request path. The live agent should execute the promoted harness. A separate worker should grade, propose, test, and promote. That is the difference between a self-evolving workflow and a system that mutates itself mid-task and cannot be rolled back. [1][2]

You can build this, but the correct target is a self-improving software system, not unrestricted self-rewriting code. The system should continuously learn from attempts, but every change must pass traces, deterministic tests, LLM judging, regression evals, security gates, and rollback rules before deployment. Trace grading is specifically designed to score end-to-end agent traces—including model calls, tool calls, guardrails, and handoffs—and identify workflow-level failures. [1][2]

## Best plan

The best plan for your goal is:

> **Build one shared Autonomous Improvement Kernel, begin with Fidelis, prove the learning loop offline, then connect Pedit, Allo, HunterXJob, and Agent Gang through project adapters.**

Do not begin by letting one large agent rewrite all five projects. Begin with a controlled **champion–challenger system**: the current version is the champion; the improvement system creates challengers, evaluates them, and promotes only candidates that measurably outperform the champion without violating safety rules. This follows the trace-and-evaluation pattern used for agent improvement: capture behavior, grade traces, convert failures into evals, propose harness changes, and validate them before deployment.
